# 令牌与信封加密

> 本篇记 kapp 系统的身份/密钥模型。参与方：[[apiserver]]（签发）、[[kapp-agent]]（持有/解密）、[[pevent]]（Job 参数携带）。
> 流程实例 → [[证书分发流程]]、[[集群接入与agent安装]]。

## 1. 令牌三件套

| 令牌 | 算法/载体 | 用途 | 生命周期 |
|---|---|---|---|
| **SubToken** | HS256 JWT，`SSEServerKey` 签 | 一证两用：SSE 订阅 + 上行 RPC Bearer | 长期（安装注入 env `KAPP_SUBSERVER_TOKEN`） |
| **NotifyToken** | JWT | 事件级一次性令牌（设计预留） | 一次性（Redis 原子 DEL 消费） |
| **Centrifugo API Key** | 静态 key | 服务端 gRPC Publish/PresenceStats | 部署配置 |

现状精确化：apiserver 的 Redis JWT 消费拦截器**被注释**；Job `--token` 主路径仍用 SubToken。NotifyToken 是契约里保留的一次性机制设计。

## 2. SubToken 与 channel 绑定

- claims：`{sub: clientName, subs: {clusterCode: {}}}`；安装时 `install.go` `Generate(clusterCode, clusterCode-random8, 0)` 签发。
- Centrifugo 用同钥 `CENTRIFUGO_TOKEN_HMAC_SECRET_KEY` 验签；apiserver 上行验签同钥。
- `subs` 是自动订阅语义而非 ACL；隔离靠 验签+私密 channel+发布垄断（详见 [[双通道通信架构]] §4）。

## 3. 主密码不出集群

企业主密码存客户集群 K8s Secret；**云端只持有盐值与密文**。两条派生路径共用 PBKDF2(600000, 64, sha256)：

| 路径 | 取字节 | 用途 |
|---|---|---|
| secrethash（启动同步） | **后 32** → SHA256 | `ReportMasterPasswordHash` 上报 hash；失败 abort 启动 |
| cert（证书分发） | **前 32** → X25519 私钥 | 解信封 DEK → AES-GCM 解 tls.key |

## 4. 信封加密结构

密文 = Base64(JSON `{d: encryptedDEK, e: encryptedData, i: IV}`)，与 kapp `pkg/secretmgr/crypto.go` 对齐：

1. X25519 私钥（PBKDF2 派生）+ `curve25519.ScalarBaseMult` 得公钥；
2. `box.OpenAnonymous` 解出 DEK（32 字节）；
3. AES-GCM(DEK, IV) 解出业务明文（tls.key）。

云侧加密时用企业公钥包裹 DEK → 只有持有主密码的集群能解。

## 5. 工程细节味

- cert `TimeoutSecs` 只约束业务处理（预留回调 RTT 余量），**上报用原始 ctx**——结果必回传。
- `createOrUpdateSecret` 对 Conflict/AlreadyExists 重试（TOCTOU），重读 ResourceVersion。
- label sanitize：`*`→wildcard、非法字符→`-`、≤63、首尾字母数字。
- 回调/上报有限重试：proxy callback 3 次×10s；cert report 3 次×10s 退避；secrethash 3 次指数退避。
