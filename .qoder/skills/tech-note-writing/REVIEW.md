# 交付前自检清单

四道硬门槛，**任一不过不得交付**。每条检查若不通过，按「处理动作」执行，不要靠模糊措辞蒙混过去。

## A. 知识点准确（最高优先级）

| # | 检查 | 处理动作（不过时） |
|---|---|---|
| A1 | **编造风险**：每条配置字段、默认值、端口、错误码、版本号、`limit`/`default` 数值是否来自官方文档或实机验证？ | 逐条分类：① 已核对 → 保留并在参考资料留链接；② 凭印象 → **用 context7 / 官方文档核对**；核不到 → 删除该具体值，改为不依赖数值的机制说明 |
| A2 | **版本错配**：示例用到的镜像 tag、SDK 版本、CRD 版本是否与配置字段的可用版本一致？跨大版本的字段是否标注"自 vN 起"？ | 全篇锁定一个版本并在开篇引述声明；无法确认的字段删除 |
| A3 | **SDK/语言混用**：Go 写法与 JS 写法是否出现在同一条链路里而未标注语言？API 名是否属于所写语言的那个 SDK（各语言 OTel/客户端 SDK API 并不同名）？ | 每段代码标注语言与包版本；不同语言的等价写法分小节列出，不做"通用伪代码" |
| A4 | **机制性错误**：是否把"通常行为"写成了"保证"？（如 at-least-once 写成 exactly-once、best-effort 导出写成不丢、有界队列写成无界） | 明确可靠性语义用词：**保证 / 默认尝试 / 尽力而为**，三选一，不用第四种说法 |
| A5 | **与既有笔记冲突**：同一组件在本 vault 的其他笔记中，版本、端口、术语、结论是否矛盾？ | 冲突时不要静默覆盖：在回复中列出冲突点，问用户以哪篇为准，并在新笔记加 `[[wikilink]]` 指向旧篇说明差异 |
| A6 | **未验证却像已验证**：实战节是否读起来像跑过？ | 未实测必须写明「按 vX 文档编写，未实际验证」；能给验证命令的一律附上预期输出 |

## B. 表达不含糊

| # | 检查 | 处理动作 |
|---|---|---|
| B1 | 是否出现"适当配置 / 做一些适配 / 基本支持 / 一般来说 / 可能需要"？ | 替换为**具体对象 + 具体动作 + 具体位置**：改哪个文件、加哪段代码、代价是什么 |
| B2 | 每层技术是否都写清了「管什么 **且** 不管什么」？"不管什么"是否点名了最容易误解的那件事？ | 补表格左列/右列；只写优点的一律补"选它的代价" |
| B3 | 数字是否有单位与量级？ | `~10x`、`默认 100`，禁止"大幅减少""很多" |
| B4 | 同一概念是否全文一个词（不混用 采集器/探针/agent、频道/主题/channel）？ | 首次出现给中英对照，后续固定其一 |
| B5 | 事实与设计判断/个人取舍是否分开？ | 判断句用「我倾向」「实践中通常」「官方不推荐」显式标记，不与规范事实同句陈述 |
| B6 | 表格/图之后是否有裸奔（无一句解读）？ | 每张表/图后补一句"这张表说明了什么"或"注意第 X 行" |

## C. 顺承合理

| # | 检查 | 处理动作 |
|---|---|---|
| C1 | **前向引用**：是否用了尚未定义的术语或后文才介绍的机制？ | 先定义再使用；或改成 `[[wikilink]]` 指向已讲过的笔记 |
| C2 | 章节顺序是否严格满足"后面每节只依赖前面已讲过的内容"？ | 重排；依赖同层概念的段落合并到同一节 |
| C3 | 第 1 节痛点是否与主角能力**一一对应**（不是通用吐槽堆砌）？ | 删掉后面没被回应的痛点，或补上对应能力 |
| C4 | 方案引出是否遵循「痛点 → 必然需求 → 方案 → 方案遗留问题 → 下一层」？ | 在"引出下一层"处补一句"〈上一层〉不管的〈Y〉，需要由谁来承担" |
| C5 | 第 5 节边界表能否回答"业务到底要不要改代码"？ | 强制输出表格：能力 × 开箱可用 × 需改动 × **具体改动点** |
| C6 | 是否存在"整节砍掉也不影响主线"的悬空内容？ | 移入 `###` 子节或删除；主线内容不得移出 |

## D. 格式符合 vault 约定

见 [VAULT.md](VAULT.md)。逐条核对：

- [ ] frontmatter：`tags`（分类 + 主题名 + 用途标签）、`created`、`updated`；日期 `YYYY-MM-DD`；tags 用列表写法
- [ ] 归属目录与命名正确；未与既有文件重名（重名 → 扩写而非新建）
- [ ] 章节全部 `## N.` 数字编号，子节 `### N.M`；无编号标题仅出现在 MOC
- [ ] 开篇 `>` 引述交代版本与整理依据
- [ ] Mermaid 代码块语法可渲染（节点文字含括号/特殊字符时用 `["…"]` 包裹）
- [ ] 表格分隔行完整（`|---|---|`），列数与表头一致
- [ ] 代码块都有语言标注；中文与英文/数字两侧空格；配置 key 用反引号
- [ ] `[[wikilink]]` 基名与实际文件名逐字一致（含空格、大小写、`&`/`+`）
- [ ] 文末 `## 参考资料` 存在，且 `## N. 一句话总结` 位于其之前
- [ ] 敏感信息：示例密钥标注"仅限本地"；不写入真实凭据

## 自审报告（必须随交付输出）

交付时在回复中给这三行，让用户知道哪里可信、哪里需要复核：

```
已核对：〈条数 / 依据来源〉
未核对：〈具体条目 + 位置〉   ← 没有则写「无」
已删除或降级：〈为了不出错而砍掉/改弱的说法〉
```
